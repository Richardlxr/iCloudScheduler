# 提醒场景验收：时段、截止、农历、重复与提醒事项

日期：2026-09-22。这一轮按“用户写下的内容就是他认为够用的信息”重新划定了阻塞与替他决定的边界。

## 产品前提

以前缺具体时刻就写进 `missing` 并要求补全，等于让用户为同一件事输入两次。现在的规则是：本机能按确定规则算出来的，一律算出来并写明依据，用户在卡片上改；只有三种情况仍然阻塞——原文自相矛盾、截图关键处无法辨认、截图里的相对日期找不到来源日期。

## 覆盖的场景与做法

| 场景 | 以前 | 现在 |
| --- | --- | --- |
| “明天下午交材料” | 只认“明天”，排到次日 09:00 | `dueDay` + `dayPart` 两个字段，本机换算到次日 15:00 |
| “周三晚上开会” | 留空要求补全 | 最近的周三 20:00 |
| “下午交” | 留空 | 今天 15:00；已过则次日 15:00 |
| “周五前交” | 周五 09:00 单次提醒 | `isDeadline`：时间对齐截止点，两天以上加提前一天的提醒，当天加提前几小时 |
| “农历八月十五聚餐” | 要求改用公历 | `lunarDate` 交给系统农历换算，全天；带时段时变成定时提醒 |
| “每周三五上午8点高数课，到1月15日” | 要求补单次日期 | `repeatRule`/`repeatDays`/`repeatUntil` 写成系统日历的重复规则 |
| 航班、面试等 | 单个提醒 | `extraReminderMinutes` 支持最多 5 个提醒 |
| “尽快办理团组织关系转入” | 日历事件，闪过即消失 | `kind="task"`，默认写入提醒事项，可勾掉、可顺延 |

换算全部在 `SchedulerCore/Timing.swift` 与 `Recurrence.swift`，以提交时刻和事件时区为准，结果必须晚于当前时间且能通过写入前的同一个解析器；夏令时缺失时刻逐小时后移。换算依据写入 `timingNote`，作为产品默认规则展示，不阻塞添加。

## 边界与保守选择

- 模型只做分类，不做日期运算：相对日期、农历、重复周期的具体日期都由本机算。词表之外的取值一律丢弃，草稿退回“需要补充时间”，绝不猜。
- 只支持 EventKit 能精确表达的重复：每天、每个工作日、每周（可指定周几）、每两周、每月、每年，外加结束日期或次数。更复杂的重复只写第一次并在 assumptions 说明。
- 重复日程的冲突检查只看第一次发生；撤销整条重复日程使用 `.futureEvents`，且仍要求指纹一致。
- 提醒事项需要独立授权。未授权或未选清单时待办继续写入日历，不会丢失；确认按钮会分别提示需要哪一种权限，授权失败不写入。
- 提醒事项的恢复核对只按保存下来的标识符查找，找不到就标记为不确定，不做全清单扫描、不自动重建。
- 全天日程仍使用设置中的固定提醒时刻，附加提醒只作用于定时日程。

## 本机结果

- 136 项核心检查：日 × 时段的具体时刻、跨夏令时对全部组合的扫描、截止提前量、农历换算（2026 中秋＝9 月 25 日、2028 闰五月十五＝7 月 7 日）、重复规则的合法性与结束条件、多提醒的去重与越界拦截、契约新字段与旧草稿解码。
- 37 项原生检查：`EKRecurrenceRule` 的频率、间隔、星期与结束条件映射，以及既有输入、附件与存储检查。
- 94 项工作流检查：待办按授权状态写入提醒事项或退回日历、卡片上切换目标、两种权限分别请求且失败不写入、重复日程一次写入并记录规则、坏的重复规则阻塞。

共 267 项离线检查。没有付费模型请求、钥匙串读取或真实日历写入。界面通过 `--review-fixture` 核对：待办卡片显示提醒事项清单与切换入口，重复卡片显示“每周三、周五 · 到 2036-01-15”，多提醒显示“提前 1 天、15 分钟提醒”。

## 未覆盖

- 未做真实的 EventKit 写入：提醒事项清单、重复日程在系统日历/提醒事项中的实际落地、跨设备同步与系统通知仍需人工验收。
- 未执行 `--model-contract-check`，六家服务商对 `dueDay`/`dayPart`/`lunarDate`/`repeatRule` 的实际遵循情况尚未联网核对。
- 改期、取消已有日程仍未实现：这类消息目前会被当作新增。

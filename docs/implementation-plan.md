# 实施计划与公开发布验收

**先用一个可安装的原生小应用验证“快捷键 → 草稿 → EventKit → 系统提醒”，再接入完整文件处理和模型预设。** 公开版本以真实工作流的可靠性为门槛，不能只展示一个能生成 JSON 的演示。

## 1. 开发前提与范围

首版面向 GitHub 开源、公众下载，最低系统建议 macOS 14。Apple Silicon 为主要测试平台；只有完成 Intel 真机测试才承诺 Intel 支持。构建目标可预留 Universal，但编译成功不能代替第二种架构的行为验证。

建议提供标准 Xcode 工程与 Swift Package 模块，依赖固定版本，确保从干净检出可以构建。源码构建者使用自己的签名身份；正式发布使用稳定的 bundle identifier 和维护者签名，降低升级后权限、Keychain 和文件路径变化带来的问题。

当前已开始实现原生开发预览，包含输入、设置、模型请求与 EventKit 写入路径。详细开发状态见 [开发与验证说明](development.md)。本计划中的付费推理、真实日历、跨设备同步、系统提醒及公开发布门槛仍需单独完成验收。

## 2. 分阶段交付

下表按一名熟悉 Swift/macOS 的开发者全职投入估算，单位为人日；各阶段以完成验收为准。合计约 28–41 人日，另留约 20% 的兼容性与修复余量，即约 7–10 周日历时间。若主要技术背景为 Web/Rust，需要额外预留 AppKit、权限和签名学习时间。

| 阶段 | 估算 | 交付物 | 通过条件 |
| --- | --- | --- | --- |
| M0 系统路径验证 | 3–5 | 菜单栏、快捷键、NSPanel、权限与测试事件、签名可安装原型 | 多显示器/全屏可输入；写到指定 iCloud 日历；另一设备可见；退出应用后系统提醒按配置触发 |
| M1 文本日程闭环 | 4–6 | 输入、单一服务、日期校验、草稿编辑、单条写入、Keychain | 从真实文字通知到日历；歧义不自动写；无效 Key/拒绝权限可恢复 |
| M2 六家模型与配置 | 6–8 | 预设设置、协议适配、分项测试、地区/模型错误处理、配置迁移 | 六个预设分别通过对应账户的文本契约；宣称图片可用的配置通过图片探测 |
| M3 文件与批量可靠性 | 6–9 | 图片/PDF、来源定位、多项确认、操作日志、部分成功与恢复、条件撤销 | 文件失败不丢输入；重启不盲目重建；重复输入有提示；撤销不误删外部修改事件 |
| M4 有限排程与体验 | 4–6 | 冲突、7 天空档安排、提醒覆盖、通用设置、无障碍与性能调优 | 不破坏已有日程；无空档时明确无解；时间规则、键盘和资源预算通过 |
| M5 公开测试与发布 | 5–7 | 回归测试、用户文档、签名公证 Release、发布流水线、贡献规则 | 干净机器安装/升级可用；隐私与兼容性说明准确；无阻断问题 |

M0 的日历测试使用明确命名的测试日历和未来测试事件，执行前选定测试范围；完成后根据测试计划清理测试事件。不能把自动化测试默认指向用户现有工作日历。

M1 完成后可以用于开发者自测；不以此替代首个公开版本对文件、图片、六家预设和提醒自定义的承诺。M0 若不能稳定满足焦点/权限/同步体验，应先解决系统路径，再投入复杂排程。

## 3. 关键技术验证清单

### 3.1 macOS 小窗口

在真实 Release 应用上验证：普通桌面、另一个 Space、全屏应用、多个显示器、外接显示器断开、Stage Manager、系统锁屏后恢复；窗口不会跑到屏幕外，也不会抢占输入法候选框。

连续呼出/隐藏 100 次，输入内容和选中状态保持稳定。文件选择器打开时不得误判为点击外部；中文组词期间 ⌘Enter 不提前提交。快捷键冲突有可操作提示，菜单栏仍可打开应用。

### 3.2 权限与沙箱

验证首次授权、拒绝、系统限制、运行中撤销、重启后重新授权；日历权限失败不影响输入和草稿。验证拖放/选择文件的沙箱访问范围，Keychain 保存/更新/删除，用户开启/关闭登录启动。

测试应使用稳定应用标识与签名；命令行片段返回权限结果不等于最终签名应用的 TCC 路径正确。Calendar entitlement 与说明字符串一并审查。[^1]

### 3.3 日历与提醒

至少覆盖：iCloud 日历、本机日历、只读订阅日历、目标日历删除、多个同名日历、账户未登录、日历同步未开启、暂时离线。首版对其他账户类型只声明经过测试的行为。

提醒测试包含开始时、提前 10 分钟、两条提醒、全天提醒、重复事件、提醒已在过去。检查系统日历保存值和真实通知分别是否符合预期；成功保存提醒不等于实际弹窗已验证。

## 4. 测试矩阵

### 4.1 自动化测试

| 范围 | 必测案例 | 验证重点 |
| --- | --- | --- |
| 日期解析 | 明天/下周、跨年、相对来源时间、闰年、无效日期 | 冻结时钟和时区，避免当前时间依赖 |
| 时区 | 上海、纽约夏令时跳变/重复、旅行起降时区 | 本地时间和 UTC 时间点一致 |
| 全天/重复 | 多日区间结束日、每周重复、截至日期 | 不偏一天，不错误展开无限序列 |
| 日程 Schema | 缺字段、未知 enum、额外动作、超长标题、过多事件 | 无效数据无法触达写入层 |
| URL | 尾斜杠、完整端点、代理前缀、错误协议、地区模板 | 不重复路径、不丢前缀、不带 Key 换主机 |
| 服务响应 | 401/403/404/429/5xx、200 HTML、空 content、截断 | 错误分类正确，不把连通当成功 |
| SSE（若启用） | UTF-8 分块、空 choices、单独 usage、断流 | 仅完整结果可进入审核 |
| 排程 | 忙碌合并、空闲事件、全天事件、任务超窗、容量不足 | 无解可解释，不越过限制 |
| 并发 | 分析中改输入、旧响应迟到、双击提交、提交中隐藏 | revision 校验、同一操作仅一个执行者 |
| 恢复 | 保存前崩溃、保存后回执前崩溃、回执后重启 | 先查明状态，不重复创建 |
| 撤销 | 外部修改、删除、标识变化、批次部分成功 | 只处理确认范围，不误删用户更改 |
| 存储 | 数据库迁移中断、旧配置加载、Key 更新 | 无明文密钥泄漏，验证状态失效正确 |

网络契约测试使用录制并脱敏的响应或模拟服务，正常 CI 不消耗模型 Key、不写真实日历。EventKit 真实集成另设人工/受控验收；模拟 Repository 通过不能被报告为 iCloud 同步通过。

### 4.2 日程质量评测集

建议建立版本化评测集：160 条文本，其中明确时间 50、相对日期 30、时区/跨日 20、重复/全天 20、缺失信息 20、来源冲突/注入 20；另加 40 张截图和 20 份短 PDF。样本使用自建合成材料或得到许可的脱敏数据，不使用私人通知原件提交仓库。

每个样本至少定义输入、referenceNow、时区、期望事件/约束、允许的合理歧义、是否必须澄清及关键字段。不要用字符串全等要求模型必须复述同一句标题；日期/时间/时区/提醒等字段要严格。

### 4.3 初始质量门槛

以下为首轮验收目标，不是现有成绩：

- 明确文本样本的关键日期/时间字段准确率 ≥98%；截图/PDF 单独报告，不混入文字成绩。
- 全量评测的最终可解析且通过业务校验比例 ≥99%；同时报告一次通过率和修复率，防止靠大量重试掩盖问题。
- 必须澄清用例在发布回归集上全部被阻止直接提交。
- 恢复、双击、网络重复回调等受控故障用例中，重复日历写入为 0；这不等于对未知环境提供绝对“恰好一次”保证。
- 未经用户确认写入、写错目标日历、无提示覆盖手工修改、跨服务商静默上传为 0；任一出现即阻断发布。

准确率以模型、模式、样本版本和测试日期共同标识。小样本结果应同时给出分子/分母，不只展示百分比；不能将试验分数解释成真实世界保证。

## 5. 性能与成本验收

| 项目 | 初始目标 | 测法 |
| --- | --- | --- |
| 已启动状态快捷键可输入延迟 | P95 ≤200 ms | 本机重复 100 次，记录快捷键回调到输入就绪 |
| 冷启动至菜单栏就绪 | P95 ≤1.5 s | Release、固定机器，多次冷启动，区分系统缓存 |
| 安装包大小 | 单一正式产物 ≤30 MB 为首轮目标 | 记录架构、压缩方式和依赖；Universal 单独解释 |
| 空闲物理内存 | 目标 ≤100 MB | 启动稳定后空闲 5 分钟，统一使用 physical footprint 指标 |
| 空闲 CPU | 五分钟平均 <单核 0.5% | 菜单栏空闲，排除主动分析 |
| 图片/PDF 峰值 | 先测量；5 张图任务目标 ≤250 MB | 同时记录最大像素、页数，结束 30 秒后检查回落 |
| 普通文字得到完整草稿 | 候选模型 P95 争取 ≤15 s | 固定网络/输入/思考设置；单独报告厂商等待 |
| 请求预算 | 常规分析 1 次，修复最多 1 次；包含所有降级/重试在内总计最多 3 次 | 从实际调用日志核对；任何重试均计费预算可见 |

不能为了达标删掉必要的时间校验，或只统计首 token 延迟。图片质量、网络等待和模型推理应分段测量；测量不达标时允许调整目标，但需解释真实瓶颈。

## 6. GitHub 开源与分发

### 6.1 仓库内容

建议首版代码选择 MIT 许可，保留所有引入依赖的许可证和第三方声明。当前实现已选择 MIT，见仓库 LICENSE。参考 CC Switch 的实质性代码若被复用，应按其 MIT 要求保留声明。[^2]

公开仓库应提供：中英文 README、构建说明、架构说明、模型兼容矩阵、隐私说明、测试说明、贡献指南、行为规范、安全问题报告方式、Issue/PR 模板、CHANGELOG 和 RELEASE_CHECKLIST。

模型兼容表显示“文档支持/最近实测日期/样本版本”，不能无证据展示所有服务“完美支持”。Issue 模板要求提供 macOS/应用版本/服务商/模型/错误代码，明确提醒不提交 API Key 或私人日历原文。

### 6.2 正式安装包

推荐 GitHub Releases 提供签名、公证后的 DMG 或 ZIP。发布链路为：构建 Release → 签名与 Hardened Runtime → 公证 → staple 票据 → 在干净机器验证 Gatekeeper、首次权限与启动 → 发布产物和校验值。Apple 公证是自动化安全检查，不是 App Store 审核。[^3]

面向公众的正常安装体验需要开发者维护正式签名身份。Apple Developer Program 页面目前标明每年 99 美元，地区本币价格以注册流程为准；源码公开并不免除正式二进制的签名分发工作。[^4]

不将关闭 Gatekeeper、关闭 SIP 或批量移除隔离属性当作普通用户安装步骤。开发者本地构建与正式 Release 分开说明。

### 6.3 CI 与密钥

普通 PR：构建、静态检查、单元/契约测试、预设 Schema 检查，不授予签名身份和供应商付费 Key。发布任务：仅可信标签/分支和受控环境可访问签名、公证密钥；第三方贡献 PR 不运行携带发布秘密的代码。

生产 API Key 永远不进入仓库、构建产物或公共日志。兼容性验收使用专用小额测试账户，人工触发并设预算上限。签名产物、发布标签与对应提交保持可追溯；不声称签名产物能做到逐字节可重现，除非另有验证。

### 6.4 更新方式

首版提供“检查更新”或跳转 GitHub Releases 的手动更新入口，安装新版本前保留数据库并运行版本化迁移。自动下载/安装更新可以后续引入，并额外完成更新签名、回滚与迁移兼容验收。

未配置官方二进制发布所需身份时，可以先发布源码和明确标注的开发构建，但不能将该状态描述成公众安装体验已经完成。

## 7. 成功发布的完整证据

| 结论 | 至少需要的证据 |
| --- | --- |
| 可以从源码构建 | 干净检出、锁定依赖、构建命令与成功日志 |
| 普通用户可以安装 | 经过签名、公证的确切产物；干净 Mac 启动记录 |
| 服务商已支持 | 特定模型/地区/适配器版本的带 Key 文本和所宣称图片测试 |
| 日历写入正确 | 目标来源与日历、读回字段、错误/恢复路径测试 |
| iCloud 跨设备同步可用 | 同一测试事件在第二设备或 iCloud 日历中可见；记录联网和账户条件 |
| 提醒可用 | 指定偏移的系统通知观察；应用退出测试与设备状态记录 |
| 没有严重可靠性问题 | 日期回归、部分成功、重复写入与撤销用例通过 |
| 达到轻量目标 | 指定 Release/硬件/系统下的大小、physical footprint、CPU 和交互延迟 |

公开 Release 的最低关闭条件：上述必需证据齐备，无权限阻断、错误日期静默写入、重复创建、误删或密钥泄漏问题；已知限制在发行说明中明确。

## 8. 推荐的首个开发批次

开始实施时，先建原生菜单栏项目、快捷键和小窗口，完成独立的 CalendarRepository，再用手工构造的有效草稿验证指定日历与提醒。随后接入单一模型和 Keychain，将文字分析闭环跑通，再扩展六家适配器。

这一批次建议保持小而完整：可安装、可输入、可审核、可保存、可看见系统提醒。它能验证本项目最重要的产品承诺，为后面的文件处理和排程提供稳定基础。
